# Lunel Architecture

## 1. 제품 정체성

루넬은 단순 일정표나 대회 사이트가 아니다. 학교 행사와 학생 프로젝트에서 발생하는
여러 사실을 하나의 상태로 수렴시키는 **오케스트레이션 코어**다.

```text
공식 일정 ─┐
비공식 일정 ├─> Lunel Core ─┬─> 학생 캘린더
프로젝트 DAG ┤               ├─> 운영 관제실
행사 규칙 ──┤               ├─> 행사별 웹
권한 정책 ──┘               └─> 스코어보드
```

행사마다 다른 것은 제목, 문제 묶음, 채점 규칙, 공개 시각, 화면 구성이다. 선행 조건,
권한, 상태 전환, 이력, 충돌 판정은 코어에서 일관되게 처리한다.

## 2. 시스템 경계

### Lunel Core

- 프로젝트 노드와 의존 관계를 DAG로 저장한다.
- `TODO → IN_PROGRESS → DONE` 등의 허용된 전환만 받는다.
- 선행 노드가 끝나지 않으면 실행·완료 명령을 거부한다.
- `expected_version`으로 동시에 편집한 상태를 감지한다.
- 담당자, 공개 가능 시각, 기한, 완료 시각을 함께 투영한다.

### Schedule Oracle

- 조회 권한이 있는 공식·비공식·프로젝트 일정을 한 시간축에 합친다.
- 겹친 시간, 동일 장소, 공식성, 중요도 구성 요소를 근거로 충돌을 분류한다.
- 높은 우선순위 일정을 유지하고 낮은 일정을 이동하는 안을 계산한다.
- 제안은 승인 전에는 절대로 원본 일정을 수정하지 않는다.

### Problem Forge

- 문제는 대회와 독립된 버전형 패키지다.
- 상태는 `DRAFT → REVIEW → READY → PUBLISHED` 순으로 승격한다.
- 공개 전 문제 본문과 최소 한 개의 검증 테스트를 요구한다.
- 수정 전 상태를 자동 스냅샷으로 남긴다.
- 학생에게는 본문과 제한만 주고 숨은 테스트, 기준 풀이, 버전 이력은 제거한다.

### Competition Runtime

- `CompetitionProblem`이 문제 패키지를 행사 문맥에 연결한다.
- 라벨, 점수, 공개·마감 시각, 스코어 설정을 행사마다 덮어쓸 수 있다.
- 선택적으로 워크플로 노드와 연결해, 준비 작업이 `DONE`이 될 때만 문제를 공개한다.
- IOI 점수제와 ICPC 해결·패널티 방식을 실시간으로 계산한다.
- 동결 이후 제출은 운영자에게만 보이고 공개 스코어보드에는 숨긴다.
- 원하는 시점의 실시간 투영을 공식 스냅샷으로 보존할 수 있다.

## 3. 권위 상태와 투영

명령과 조회를 구분한다.

- **명령**: 문제 상태 승격, 노드 전환, 제출, 판정, 행사 상태 변경
- **투영**: 현재 실행 가능 작업, 학생별 보이는 문제, 라이브 순위, 일정 충돌

프런트엔드는 상태를 추측하지 않는다. 엔진의 투영 결과에 있는 `ready`,
`blocked_by`, `frozen` 값을 표시한다. 이 원칙 덕분에 모바일 웹, 운영 대시보드,
행사 전용 웹이 서로 모순된 상태를 만들지 않는다.

## 4. 채점 경계

루넬 API 프로세스는 비신뢰 소스 코드를 실행하지 않는다.

- 단답·출력 문제: `EXACT`, `TOKENS`, `FLOAT` 내장 비교기
- 특수·상호작용·수동 문제: `MANUAL_REVIEW`
- 소스 코드: `QUEUED` 후 격리된 외부 샌드박스 어댑터

샌드박스는 네트워크 차단, 읽기 전용 실행 이미지, CPU·메모리·시간 제한, 임시
파일시스템, 프로세스 수 제한을 가져야 한다. 채점 결과만 운영자 판정 API를 통해
루넬의 권위 상태로 되돌린다.

## 5. 권한과 보안

- 역할: 학생, 교사, 관리자, 외부 사용자
- 범위: 공개, 로그인 사용자, 그룹, 역할, 그룹+역할, 절차적 키
- 문제 제작·대회 운영은 교사와 관리자만 수행한다.
- 일반 사용자는 자신의 제출만 조회한다.
- 비공개 스코어보드는 운영자만 조회한다.
- Redis가 없는 개발 환경은 프로세스 로컬 토큰 폐기 저장소를 사용한다.
- 운영 환경에서 Redis 폐기 저장소가 실패하면 인증을 계속하지 않고 `503`을 반환한다.

## 6. 현재 완성된 흐름

1. 교사가 문제 패키지를 만든다.
2. 본문·테스트 그룹·테스트 케이스·기준 풀이를 구성한다.
3. 검수 상태를 거쳐 공개 가능 상태로 승격한다.
4. 행사에 대회 런타임을 만들고 문제를 연결한다.
5. 필요하면 문제 공개를 프로젝트 DAG 노드 완료에 종속시킨다.
6. 학생이 참가하고 단답 또는 코드를 제출한다.
7. 내장 비교기 또는 외부 샌드박스/운영자가 판정한다.
8. 루넬이 IOI/ICPC 스코어보드를 실시간 투영하고 동결을 적용한다.
9. 운영자가 최종 상태를 스냅샷으로 보존한다.

## 7. 다음 확장 지점

- gVisor/Firecracker 기반 실제 코드 샌드박스 어댑터
- 학교 학사 시스템·Google Calendar·메신저 동기화 커넥터
- 일정 조정안 승인 명령과 다자 승인 규칙
- 문제 패키지 ZIP import/export 및 validator 실행
- 팀 참가, clarification, rejudge, hack/testlib 연동
- PostgreSQL row-level security와 감사 로그 서명

이 항목들은 코어의 경계를 바꾸지 않고 어댑터로 확장한다.
